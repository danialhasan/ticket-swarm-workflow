## 5. The Software Factory Trap

The “Software Factory Trap” is thinking the future is just:

```text
more agents
doing more tasks
with bigger context windows
and better prompts
```

That is the shallow version.

The real unlock is not “more autonomous workers.”

The real unlock is the operating system around the workers:

* missions
* decomposition
* skill routing
* contracts
* requirements
* traceability
* artifacts
* receipts
* verification
* review
* adversarial critique
* feedback loops
* regression pressure
* harness optimization

A software factory is not a pile of agents.

A software factory is the discipline layer that turns messy work into repeatable output.

## 6. The Old Engineering Discipline Angle

A lot of this is not new.

That is the point.

We are not inventing all of this from scratch.

Past engineers already developed many of the right ideas:

* NASA-style work breakdown structures
* requirements engineering
* mission planning
* decomposition
* review gates
* traceability
* verification artifacts
* acceptance criteria
* handoff discipline
* proof of work
* adversarial review

The problem was not that the ideas were wrong.

The problem was that they were expensive to operate.

Humans had to manually:

* write every requirement
* maintain every trace link
* update every review artifact
* enforce every handoff
* check every dependency
* keep every document alive
* make every review useful

AI changes the economics.

Models make it possible to reimagine old engineering systems as living, executable harnesses.

Key line:

> The future is hiding inside the engineering ideas that were too expensive to run.

Another version:

> AI does not erase requirements engineering, mission planning, or verification. It makes them executable.

## 11. Plan Mode vs Mission Mode

This distinction is important.

Plan mode:

```text
interpret goal
select candidate skills
reject wrong skills
surface missing inputs
identify risks
propose execution path
declare expected receipts
```

Mission mode:

```text
execute selected skills
record tool calls
produce artifacts
produce receipts
capture trace
surface failures
prepare review package
```

The key:

> Plan mode decides. Mission mode acts.

This prevents agents from freeforming their way through ambiguous work.

## 12. Skills Under Contract

The 23 skills should not be presented as “I have a lot of tools.”

That is feature-tour energy.

Instead:

> The skills are reusable engineering capabilities, but they only become reliable when selected under contracts.

Each skill should eventually have a manifest:

```text
purpose
when_to_use
when_not_to_use
required_inputs
outputs
side_effects
risk_level
mode_allowed
preconditions
postconditions
failure_modes
examples
counterexamples
```

This is what turns a bag of tools into a harness.

Key line:

> A skill without a contract is just another way for an agent to be confidently wrong.

## 13. Receipts

Receipts are how the system avoids fake success.

A receipt answers:

```text
What was done?
What artifact was produced?
What evidence supports it?
Which requirement or mission objective does it satisfy?
What remains unresolved?
```

Receipts matter because agents are good at producing plausible completion.

The harness needs proof, not vibes.

Key line:

> The future software factory does not just produce artifacts. It produces proof that the artifacts mean what they claim.

---

## 14. Adversarial Review

Adversarial review is how the system resists self-congratulation.

The agent that builds should not be the only agent that judges.

A fresh context can challenge:

* missing requirements
* dropped constraints
* weak evidence
* hallucinated completion
* wrong skill selection
* unsupported claims
* bad handoffs
* overconfident summaries

The role split:

```text
Builder Codex:
proposes or implements

Adversarial Codex:
tries to break the result

GPT Pro:
synthesizes, resolves, turns critique into next work orders
```

Key line:

> Review is not a vibes check. It is pressure.

---

## 15. Feedback Descent

Feedback Descent is the next upgrade because scalar rewards are too thin for this kind of system.

A scalar reward says:

```text
bad
```

Trace-linked critique says:

```text
what failed
where it failed
why it failed
what artifact caused it
what should change next
```

The improvement loop:

```text
failed run
→ trace
→ typed failure code
→ grounded critique
→ candidate artifact mutation
→ regression eval
→ promotion or rejection
```

The artifacts to optimize are not only prompts.

They include:

* skill manifests
* routing policies
* plan-mode prompts
* mission-mode prompts
* middleware templates
* review rubrics
* proof package formats
* failure-code taxonomies
* eval fixtures

Key line:

> Feedback Descent should optimize the harness, not just the prompt.

## 18. Strong Closing Script

What I’ve shown is not just a Codex workflow.

It’s an early software-factory pattern.

Agents are powerful, but they’re messy. So the interesting work is not just prompting them harder. It’s building the harness around them: missions, skills, contracts, receipts, review, and feedback.

A lot of this is old engineering discipline: requirements, decomposition, traceability, verification. The difference is that AI changes the economics. What used to be too expensive to run continuously can now become part of the living system.

That is the alpha.

The future is hiding inside the engineering ideas that were too expensive to run.

Given the timeline we’re living in, this is the part of the tech tree I want to explore: not just better agents, but better systems for organizing agent work.

Because if we get that right, we do not just make coding faster.

We change what it feels like to build software.
