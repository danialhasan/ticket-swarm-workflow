2.4

Why do agents like Codex fail in this context?

  • Code shows what changed, but not why it mattered.
  • Agents can edit files without knowing the real decision.
  • When proof is missing, review becomes detective work.
The reason the previous problems exist is that code is only the executable surface of a larger object. The runtime does not need requirements, derivation, customer context, source authority, or proof obligations, so those things disappear unless the workflow captures them. Agents mostly see the visible codebase. If they are asked to extend a system from that partial context, they produce syntactically correct and semantically incomplete work. That is why the bottleneck moves from code generation to trusted outcomes.
2.5

So how do we fix it?

We look for what engineers in the 90s came up with, encode those into skills, and serve them in the harness.

This is the transition. The Dvorak discovery call made the shape concrete: teams were already building a homegrown docs, specs, orchestration, tests, and review machine around agents, and the tax was maintaining that machine. The exact old ideas are requirements discovery, source authority, fit criteria, traceability, work breakdown, proof surfaces, verification, review packets, and staleness. The new move is to encode those ideas into skills and serve them in the harness so the agent can actually run the doctrine instead of hearing it as advice.
2.5.1

We turn old engineering discipline into skills Codex can run.

requirements engineering Turn messy intent into claims we can verify.
implementation contracts Tell Codex what to change and what not to touch.
execution orchestration Split work into lanes agents can own.
layered verification Match each claim to the proof that actually checks it.
receipt closeout Leave links a human or agent can audit later.
This is the map before the examples. The point is not that one book or one method solves agents. The plugin borrows old engineering discipline and turns it into runtime sections: requirements engineering, planning contracts, execution orchestration, review reconciliation, and release handoff. Requirements and orchestration are the two examples I will expand because they are where the agent failure mode is easiest to see.
2.6

Plan mode is too naive when requirements are recursive.

Requirements engineering solves these problems:

  • One prompt hides multiple actors, scenarios, and business contexts.
  • Plans jump to implementation before asking what must be true.
  • Source authority, fit criteria, and risky assumptions stay implicit.
  • Proof gets substituted: screenshots for state, backend tests for journeys.
  • Review becomes reconstructing intent from a plausible final diff.
This is the biggest one. Normal plan mode in AI apps is too naive for real engineering work because requirements are recursive. The agent makes a plan from the prompt, but the plan itself reveals missing actors, scenarios, constraints, source authority, and proof questions. Requirements engineering gives us the better loop: discover, classify, split, validate, and only then plan execution. For Codex, that means a vague prompt becomes requirement rows: actor, scenario, claims, type, fit criterion, source, assumptions, proof surface, forbidden proof substitutions, autonomous verification, and the human judgment packet.
2.6.1

Requirements engineering makes plans better.

The extra context gives Codex something concrete to verify against.

actors and scenarios Who it matters to, the business context, and the scenario they are in.
distinct claims Each user, system, state, permission, and review claim is split apart.
source authority Which code, doc, ticket, customer source, or external source is allowed to decide.
fit criteria and proof What must be true, and which proof surface can actually validate it.
forbidden substitutions Auth flow: screenshot is not enough.
Need traces and DB verification.
verification and judgment What the agent verifies autonomously, and what the human still has to judge.
This is what requirements engineering adds before Codex plans execution. It forces the prompt to become actors, scenarios, distinct claims, source authority, assumptions to falsify, fit criteria, proof surfaces, forbidden proof substitutions, autonomous verification, and the human judgment packet. The point is not a bigger plan. The point is a map Codex can verify against, so review does not become reconstructing intent from a mystery diff.
2.6.2

Without requirements engineering, Codex writes a plausible plan.

The plan makes sense, but it waves away too much detail, and that's how agents produce garbage.

This is what the naive plan looks like. It is not wrong in an obvious way. That is the problem. The plan sounds scoped and professional, but it does not say who the actor is, which claim is being made, which source has authority, what assumption could be false, what proof surface validates the result, or what the reviewer should judge. It compresses everything into implementation activity.
2.6.3

With requirements engineering, Codex writes a verifiable map.

The extra detail makes it easy to catch issues before they happen, and makes agentic work easier to verify. This means you can delegate more ambitious work with Codex.

This is the same kind of task with requirements engineering turned on. The output is larger, and for bigger projects it can become a lot to review. But the extra context changes what verification means. Codex now has claims, actors, fit criteria, proof surfaces, and assumptions to check against. The reviewer is no longer reconstructing intent from the final diff.
2.7

Agents must be taught how to orchestrate their workers.

Execution orchestration solves these problems:

  • Agents collide when no one owns the lane.
  • Tests break when another lane changes the contract.
  • The human gets stuck merging everything by hand.
Once requirements are split, the next failure is orchestration. Agents can spin up workers, but without a work breakdown and execution map they collide. The problems show up as two workers changing the same component, tests written against stale state, UI and backend lanes disagreeing on contract names, shared resources being mutated in parallel, and the human having to reconcile branches before verification can even begin. WBS is the source discipline underneath the execution map: define owned work objects, interfaces, dependencies, proof obligations, and completion criteria before workers start.
2.7.1

Execution orchestration makes delegation safe.

It turns approved work into owned, isolated, verifiable lanes.

lane ownership Which worker owns which product seam, file surface, and proof obligation.
dependency waves What can run together, and what must wait for another lane to land.
serialized resources Shared runtimes, DB state, Electron slots, and deploy surfaces that cannot collide.
worktree isolation Dedicated branch and worktree lanes for mutating parallel work.
proof responsibility Each lane knows what evidence it must leave behind before review.
review convergence How isolated work collapses back into one human-judgable packet.
Execution orchestration is where delegation becomes concrete. The plugin does not just say spawn workers. It asks which tickets or seams can run together, which surfaces collide, which resources must serialize, which branch or worktree owns each lane, what proof each lane is responsible for, and how the work will converge for review. Without that map, parallel agents look busy but create review chaos.
2.7.2

Without execution orchestration, Codex creates busy workers.

The work splits, but ownership does not. That is how agents collide.

This is the failure mode. Codex can create workers, but if the lanes are vague, the workers collide. Two agents can touch the same files, assume the same runtime slot, duplicate work, or optimize locally while breaking the larger contract. The plan feels parallel, but it has not made ownership real.
2.7.3

With execution orchestration, Codex delegates owned work.

Parallelism becomes reviewable because every lane has a boundary, proof target, and convergence path.

With execution orchestration, Codex does not just parallelize. It assigns ownership. The lane map says what can run together, what must serialize, what each lane owns, what proof it must leave behind, and where the work converges for review. That makes bigger delegated work safer because the human is not untangling a pile of agent activity at the end.
2.7.4

With execution orchestration, Codex delegates owned work.

Parallelism becomes reviewable because every lane has a boundary, proof target, and convergence path.

The second step is the execution map. In the Codex clip, capture the execution-orchestration skill producing Mermaid dependency diagrams, execution waves, lane ownership, serialized-resource notes, proof targets, and convergence. This is the difference between parallel agent activity and delegated work that remains reviewable.
2.10

Implementation starts when `/goal` executes a signed-off Linear contract.

By this point, Codex is not discovering what to build from scratch. It is executing a contract that already contains the seam, lanes, and proof obligations.

/goal execution entrypoint The user points Codex at the implementation ticket, not a loose prompt.
Linear implementation contract Requirements engineering and execution orchestration are already compiled into the ticket.
dev/test composition Codex enters the multi-agent implementation, review, patch, and verification loop named by the contract.
This is the jump into implementation. We are not redoing requirements engineering or orchestration. The assumption is that those have produced a signed-off implementation contract in Linear. The demo entrypoint is slash goal, but slash goal is no longer a vibe prompt. It points Codex at a contract: one seam, non-goals, source of truth, lane plan, dev test composition, layered verification, and receipt targets.
2.10.1

The implementation contract embeds the orchestration and proof plan.

The ticket is structured so Codex can spend compute without expanding scope.

seam The one product surface, backend boundary, or runtime behavior being changed.
non-goals Explicit surfaces, ideas, and shortcuts Codex must not touch.
source of truth Canon, current runtime state, contract rows, DB/API surfaces, and allowed local state.
lane map Worker ownership, worktrees, file surfaces, dependencies, and serialized resources.
dev/test composition Multi-agent implementation, non-author review, patch loop, and re-review path.
verification matrix The required proof layers and receipt targets before closeout can be trusted.
This slide explains why implementation can start at two point ten without rehashing the earlier section. The implementation contract is the bridge. It names the seam, non-goals, source of truth, lane map, dev test composition, verification matrix, and receipt targets. For the demo visual, use a Mermaid diagram where the overall plan fans out into implementation-contract nodes, each with its own scope, owner, dependencies, and proof obligations. That is how requirements engineering and execution orchestration show up during implementation: they are embedded in the ticket before Codex starts writing code.
2.10.2

Implementation is an iterative dev, review, and patch loop.

The code change is only one step inside the contract-owned loop.

read contract Load the seam, proof matrix, lane ownership, and forbidden scope.
inspect code Find the existing primitives, state owners, commands, and tests.
implement Make the smallest green change inside the owned surface.
review + patch Non-author review finds drift, bugs, missing proof, and abstraction mistakes.
receipt Leave evidence, non-claims, and any remaining HOLD for the next gate.
This is the implementation loop. Codex reads the contract, inspects code, implements the smallest green change, runs non-author review, patches issues, and leaves receipts. The important point is that implementation is not one codegen moment. It is where Codex spends compute, but the compute is bounded by the contract. Repeated failures become blockers or split signals, not hidden summaries.
2.11

Layered verification lets you trade compute for robust engineering.

Every layer is considered, then run, marked not required, or held with a reason.

repo floor lint, typecheck, test, build
property invariants and generated cases
unit local behavior and edge cases
contract API, schema, command, or component contract
model prompt, eval, trajectory, or model behavior proof
integration cross-module and runtime interaction proof
smoke the smallest live path that should not break
DB-backed persisted state, RLS, query, or projection proof
Electron / UI renderer, route, click path, and visible green state
Computer Use human-like journey proof in the real app surface
telemetry runtime queries that distinguish happy and negative paths
receipt one verdict: VERIFIED, PARTIAL, or UNVERIFIED
This is the layered verification slide. The key line is that layered verification lets you trade compute for robust engineering. Every ticket owes the repo floor unless explicitly not applicable: lint, typecheck, test, and build. Then Codex considers property, unit, contract, model, integration, smoke, DB-backed proof, Electron or UI proof, Computer Use journey proof, telemetry or runtime queries, and a final receipt verdict. Not every ticket needs every layer, but every layer has to be considered honestly.
2.11.1

Pick the verification layer for the part of the app you changed.

Different parts of the app need different verification layers.

backend contract API, contract, integration, and endpoint proof.
durable state DB-backed write, projection, RLS, query, or telemetry proof.
UI journey Electron route proof, click path, screenshots, and visible state.
human interaction Computer Use walkthrough or human runtime QA packet.
model behavior Eval, trace, trajectory, or dataset-backed repair proof.
This is the explanatory slide after the layer list. The mistake is to run a familiar command and call it proof. The verification layer should match the part of the app that changed. Backend contracts need contract or integration proof. Durable state needs DB-backed proof. UI journeys need route and click proof. Human interaction can need Computer Use or human runtime QA. Model behavior needs evals, traces, trajectories, or datasets. This ties back to the requirements section: proof has to match the work.
2.12

Closeout tells the human exactly what to review.

The packet links each result to the proof or blocker behind it.

  • Start with a short review index.
  • Show what passed, what is blocked, and what was not claimed.
  • Link the exact receipts the human should inspect.
  • Keep proof gaps visible beside the evidence.
This is the closeout slide. The point is human review. Bring the closeout markdown document onto the screen and show that it tells the human exactly what to inspect: what passed, what is blocked, what was not claimed, and which receipt links prove each part. The human should not have to reconstruct the whole run from summaries or raw artifacts.
